# 六堡茶智能服务平台功能实现文档

本文档说明项目中各功能模块的实现方式，覆盖微信小程序端、FastAPI 后端、数据库、AI 模型与知识库检索流程。

## 1. 系统整体架构

项目采用“微信小程序 + FastAPI 后端 + SQLite 数据库 + AI/RAG 模块”的分层结构。

- 小程序端位于 `miniapp/`，使用原生 WXML、WXSS、JavaScript 实现页面交互。
- 后端位于 `backend/`，使用 FastAPI 提供 REST API，入口为 `backend/main.py`。
- 数据层使用 SQLAlchemy，开发环境默认 SQLite，生产环境可切换 MySQL。
- AI 能力位于 `ai_models/`，包括 YOLOv8 图像识别、Ollama/Qwen2.5 LLM、BGE/FAISS RAG 检索。
- 原始知识文档位于 `knowledge_base/`，启动时导入数据库，并用于构建向量索引。

后端启动流程：

1. 执行 `python run.py` 启动 Uvicorn 服务。
2. `backend/main.py` 加载 `.env` 环境变量。
3. FastAPI lifespan 中调用 `init_database()` 初始化数据库。
4. 将 `knowledge_base/**/*.txt` 导入 `knowledge_base` 表。
5. 调用 `VectorStore().build_if_needed()` 构建或加载 FAISS 索引。
6. 注册用户、识别、问答、知识库、历史、地图、日记、测验、估价、推荐等路由。

## 2. 通用请求封装

前端统一通过 `miniapp/utils/request.js` 发送请求。

实现方式：

- `request(options)` 负责普通 HTTP 请求。
- GET 和 DELETE 请求会把 `data` 拼接为 query string。
- POST 和 PUT 请求会把 `data` 放入 JSON body。
- 后端返回 `code !== 0` 时，前端按业务错误处理并进入 `catch`。
- `uploadFile(filePath, formData)` 封装 AI 识别图片上传，请求 `/api/recognition`。
- `uploadJournalImage(filePath, openid)` 封装品茶日记图片上传，请求 `/api/journal/upload`。
- `BASE_URL` 来自 `miniapp/utils/config.js`，本地调试可配置为 `http://127.0.0.1:8001`，真机调试可配置为内网穿透地址。

后端通用能力：

- `RateLimitMiddleware` 提供基于 openid 或 IP 的简单限流。
- `RequestLoggingMiddleware` 为每个请求生成 request id 并记录耗时。
- `register_exception_handlers()` 注册全局异常处理。
- `backend/utils/validators.py` 提供 openid、昵称、问题、分页、HTML 内容等输入清理函数。

## 3. 用户登录与个人中心

涉及文件：

- 前端：`miniapp/pages/login/login.js`、`miniapp/pages/profile/profile.js`、`miniapp/app.js`
- 后端：`backend/api/user.py`
- 模型：`backend/models/user.py`
- 微信工具：`backend/utils/wechat.py`

实现方式：

1. 小程序启动时执行 `app.js` 中的 `onLaunch()`。
2. 如果本地缓存中已有 `openid`，调用 `/api/user/profile` 校验用户是否存在。
3. 如果没有缓存，则跳转到登录页。
4. 登录页调用 `wx.login()` 获取微信临时 `code`。
5. 前端请求 `/api/user/login/wechat`，后端通过 `code2session()` 向微信接口换取真实 openid。
6. 如果没有配置 `WECHAT_APP_ID` 或 `WECHAT_APP_SECRET`，后端会降级为开发模式，生成 `dev_` 开头的 openid。
7. 后端查询用户是否存在，不存在则创建默认昵称为“茶友”的用户。
8. 前端再调用 `/api/user/profile` 的 PUT 接口保存用户头像和昵称。
9. 登录信息保存到 `globalData` 和本地 storage，其他页面从缓存或 `getApp().globalData` 获取 openid。

个人中心实现：

- 通过 `/api/user/profile` 获取用户资料。
- 通过 `/api/history` 获取历史记录统计。
- 通过 `/api/favorite` 获取收藏统计。
- 通过 `/api/user/profile` PUT 更新昵称和头像。
- 后端会对昵称、头像地址做长度限制和危险字符清理。

## 4. 首页模块

涉及文件：

- 前端：`miniapp/pages/index/index.js`
- 后端：间接调用 `/api/knowledge/search/query`

实现方式：

- 首页的茶知识卡片、快捷问题、季节推荐在前端本地配置。
- `setSeason()` 根据当前月份生成季节推荐内容。
- 点击知识卡片时，根据卡片对应关键词请求 `/api/knowledge/search/query`。
- 如果搜索结果带有知识文章 ID，则跳转到 `pages/knowledge/detail`。
- 如果没有匹配文章，则把待提问内容写入 `app.globalData._pendingQuestion`，切换到聊天页自动提问。
- 快捷问题同样通过 `globalData._pendingQuestion` 传递给聊天页，因为 `switchTab` 不支持 query 参数。

## 5. AI 病害识别

涉及文件：

- 前端：`miniapp/pages/identify/identify.js`
- 请求封装：`miniapp/utils/request.js`
- 后端路由：`backend/api/recognition.py`
- 业务服务：`backend/services/recognition_service.py`
- 模型推理：`ai_models/yolo/predict.py`
- 数据模型：`backend/models/record.py` 中的 `RecognitionRecord`

实现方式：

1. 用户在识别页选择拍照或相册图片，前端调用 `wx.chooseMedia()`。
2. 前端通过 `uploadFile()` 使用 `wx.uploadFile()` 上传图片。
3. 请求携带 `openid` 和 `task=disease`，后端接口为 `/api/recognition`。
4. 后端先校验用户是否登录。
5. 后端校验图片类型，仅允许 JPG、PNG、WEBP。
6. 后端限制图片大小不超过 10MB。
7. `recognition_service._compress_image()` 使用 Pillow 将图片压缩到最长边 1280 像素以内，保留较高画质用于病害识别。
8. 图片保存到 `backend/uploads/`，并生成 `/uploads/xxx` 相对访问路径。
9. `predict_image()` 调用 YOLOv8 权重 `ai_models/yolo/best.pt` 进行检测。
10. 推理结果包括识别类别、置信度、结果说明、处理建议。
11. 后端将识别结果写入 `recognition_record` 表。
12. 前端把置信度转换为百分比并展示结果，同时拼接 `BASE_URL + image_url` 显示上传图片。

识别降级逻辑：

- 如果 `best.pt` 不存在，返回“模型未加载”，提示放置模型权重。
- 推理前会做简单叶片颜色预检，明显不是茶叶图片时返回“非茶叶图片”。
- YOLO 未检测到目标时返回“未检出茶叶”。
- 病害目标置信度偏低时返回“识别不确定”。
- 正常叶片类别会返回“未检出明显病害”。

当前支持的识别类别包括：

- 茶黑腐病
- 茶褐斑病
- 茶落叶病
- 红蜘蛛危害
- 茶小绿叶蝉危害
- 正常茶叶
- 茶白星病
- 茶叶病害

## 6. 智能问答

涉及文件：

- 前端：`miniapp/pages/chat/chat.js`
- 后端路由：`backend/api/chat.py`
- 业务服务：`backend/services/chat_service.py`
- RAG 生成：`ai_models/rag/generator.py`
- LLM 客户端：`ai_models/llm/ollama_client.py`
- 数据模型：`backend/models/record.py` 中的 `QARecord`

实现方式：

1. 用户在聊天页输入问题，前端收集当前对话历史。
2. 前端请求 `/api/chat`，提交 `openid`、`question`、`history`。
3. 后端校验用户是否登录。
4. 后端使用 `sanitize_question()` 清理问题文本。
5. `ask_question()` 调用 `rag_answer()`。
6. `rag_answer()` 先调用 `retrieve(question, top_k=3)` 从知识库召回相关文档。
7. 将召回结果拼接为“参考资料”上下文。
8. `chat_completion()` 将系统提示词、最近 6 条对话历史、参考资料和用户问题发送给本地 Ollama 的 Qwen2.5 模型。
9. LLM 返回回答后，后端保存问答记录到 `qa_record` 表。
10. 接口返回回答、参考来源和相关推荐文章标题。
11. 前端在消息列表中展示 AI 回答、参考资料和推荐内容。

问答降级逻辑：

- Ollama 未启动、模型未拉取或调用失败时，`chat_completion()` 返回本地兜底回答。
- 如果有 RAG 上下文，本地兜底回答会截取知识库内容进行整理。
- 如果没有 RAG 上下文，则返回六堡茶领域的通用提示。
- LLM 调用失败时会进行指数退避重试，最终失败则使用本地兜底回答。

## 7. RAG 知识库检索

涉及文件：

- 原始文档：`knowledge_base/`
- 数据导入：`backend/database/init_db.py`
- 后端服务：`backend/services/knowledge_service.py`
- 检索入口：`ai_models/rag/retriever.py`
- 向量库：`ai_models/rag/vector_store.py`
- 嵌入模型：`ai_models/rag/embedding.py`

实现方式：

1. 项目启动时扫描 `knowledge_base/**/*.txt`。
2. 每个 txt 文件按文件名作为标题，文件内容作为正文，父目录作为分类。
3. 数据导入到数据库 `knowledge_base` 表。
4. `VectorStore` 同样扫描所有 txt 文档，构建向量检索 chunk。
5. `embed_texts()` 调用硅基流动 BGE embedding 接口生成向量。
6. 如果没有配置 `SILICONFLOW_API_KEY`，则使用本地确定性伪向量，保证流程能运行。
7. FAISS 使用 `IndexFlatIP` 做内积相似度检索。
8. 索引保存到 `ai_models/rag/index/faiss.index`，元数据保存到 `meta.json`。
9. 检索时对 query 生成向量，返回 top_k 文档、分数、来源和分类。

索引维护逻辑：

- 如果索引文件存在，会先尝试加载。
- 如果当前 embedding 维度和索引维度不一致，会删除旧索引并重建。
- 如果 FAISS 或向量服务不可用，则检索结果为空，业务层可回退到 SQL 模糊搜索。

## 8. 知识库列表、搜索与详情

涉及文件：

- 前端：`miniapp/pages/knowledge/knowledge.js`、`miniapp/pages/knowledge/detail.js`
- 后端路由：`backend/api/knowledge.py`
- 后端服务：`backend/services/knowledge_service.py`
- 模型：`backend/models/knowledge.py`

实现方式：

- `/api/knowledge` 返回知识库列表，支持 `category`、`page`、`page_size`。
- 前端按分类 tab 传入 `history/process/culture/health/brew/grade/origin`。
- 后端按分类筛选并分页返回文章摘要。
- 摘要使用正文前 200 字生成。
- 接口返回 `total`、`page`、`page_size`、`has_more`。
- 前端使用 `loadMore()` 实现分页加载。
- `/api/knowledge/search/query` 先走 RAG 向量检索。
- 向量结果缺失时，后端用 SQL `LIKE` 在标题和正文中模糊查询。
- 搜索结果会根据标题匹配数据库记录，附加文章 ID，方便前端跳转详情。
- `/api/knowledge/{kid}` 返回完整文章内容。

缓存实现：

- `knowledge_service.py` 内部使用简单内存缓存 `_cache`。
- 列表、详情、搜索结果缓存 5 分钟。
- 缓存 key 包含分类、页码、页大小、搜索词等参数。

## 9. 历史记录

涉及文件：

- 前端：`miniapp/pages/history/history.js`
- 后端路由：`backend/api/history.py`
- 数据模型：`RecognitionRecord`、`QARecord`

实现方式：

1. 用户进入历史页，前端从缓存或全局数据获取 openid。
2. 请求 `/api/history`，参数包括 `openid`、`type`、`page`、`page_size`。
3. 后端校验用户是否存在。
4. `type=all` 时同时返回识别历史和问答历史。
5. `type=recognition` 时只返回识别记录。
6. `type=qa` 时只返回问答记录。
7. 两类记录均按创建时间倒序排列。
8. 返回结果包含分页信息和 `has_more`。
9. 识别历史中的图片相对路径由前端拼接 `BASE_URL` 展示。

删除实现：

- 删除识别记录：`DELETE /api/history/recognition/{rid}`。
- 删除问答记录：`DELETE /api/history/qa/{qid}`。
- 删除时会同时校验记录是否属于当前 openid 对应用户，避免删除他人数据。

## 10. 收藏功能

涉及文件：

- 前端：`miniapp/pages/favorites/favorites.js`、`miniapp/pages/chat/chat.js`、`miniapp/pages/knowledge/detail.js`
- 后端路由：`backend/api/history.py`
- 数据模型：`backend/models/record.py` 中的 `Favorite`

实现方式：

- 收藏接口为 `POST /api/favorite`。
- 请求参数包括 `openid`、`fav_type`、`target_id`、`title`、`content`。
- `fav_type` 支持 `knowledge`、`qa`、`recognition`。
- 非法收藏类型会被规范化为 `knowledge`。
- 标题和内容会通过 `sanitize_html()` 去除 HTML 标签和危险字符。
- 收藏列表接口为 `GET /api/favorite`，支持分页。
- 取消收藏接口为 `DELETE /api/favorite/{fid}`。
- 删除时校验收藏记录必须属于当前用户。

前端使用场景：

- 聊天页可收藏最后一条 AI 回答。
- 知识详情页可收藏文章。
- 收藏页集中展示收藏内容并支持取消收藏。

## 11. 产区地图与路线规划

涉及文件：

- 前端：`miniapp/pages/map/map.js`
- 地图工具：`miniapp/utils/mapService.js`、`miniapp/utils/qqmap-wx-jssdk.js`
- 后端路由：`backend/api/region.py`
- 后端服务：`backend/services/region_service.py`
- 数据模型：`backend/models/region.py`
- 种子数据：`backend/database/init_db.py`

实现方式：

1. 后端初始化时向 `regions` 表导入 7 个六堡茶产区。
2. 产区数据包含名称、位置、经纬度、介绍、代表品牌、采摘季节、产量、品质特点、产区等级。
3. 前端进入地图页后请求 `/api/regions`。
4. 后端按 `level` 和 `id` 排序返回产区列表，核心区优先。
5. 前端把产区转换成地图 markers，不同等级使用不同颜色。
6. 前端调用 `wx.getLocation()` 获取用户当前位置。
7. 用户位置作为额外 marker 展示。
8. `calcDistance()` 使用 Haversine 公式计算用户到产区的直线距离。
9. 点击产区 marker 展示产区详情弹窗。

地点搜索实现：

- `getSuggestion()` 使用腾讯地图 SDK 做输入联想。
- 确认搜索时优先调用 geocoder 做地址解析。
- 地址解析失败时降级为 POI 搜索。
- 搜索结果会作为蓝色 marker 添加到地图。

路线规划实现：

- 前端调用腾讯地图 Direction API。
- 支持 driving、walking、bicycling 等模式。
- `planRoute()` 请求腾讯地图路线接口。
- `decodePolyline()` 解码腾讯地图压缩 polyline。
- 前端将路线绘制为 map 组件的 polylines。
- `formatDistance()` 和 `formatDuration()` 格式化路线距离和耗时。

## 12. 制作工艺流程

涉及文件：

- 前端：`miniapp/pages/process/process.js`
- 后端：`backend/api/process.py`

实现方式：

- 后端在代码中定义 `PROCESS_PHASES` 和 `PROCESS_STAGES`。
- `PROCESS_PHASES` 表示工艺阶段：初制工艺、精制工艺、陈化存储。
- `PROCESS_STAGES` 表示具体步骤：采摘、杀青、揉捻、渥堆发酵、复揉、干燥、陈化。

- 前端请求 `/api/process` 获取完整流程。
- 页面保存完整数据到 `allStages`，用于本地筛选。
- 点击阶段 tab 时，根据阶段名称筛选对应步骤。
- 点击具体步骤时，前端打开详情弹窗展示工艺说明。

## 13. 冲泡指南与计时器

涉及文件：

- 前端：`miniapp/pages/brew/brew.js`

实现方式：

- 冲泡指南是纯前端功能，不依赖后端接口。
- 页面内置茶类配置，包括六堡茶、生普洱、熟普洱、红茶、绿茶、白茶。
- 每种茶配置水温、茶水比、第一泡时间、每泡递增时间和说明。
- 用户选择茶类后，点击开始冲泡。
- 当前泡计时公式为：`firstTime + increment * steepCount`。
- 使用 `setInterval()` 每 200ms 刷新剩余时间。
- 使用 `Date.now()` 和 `endTimestamp` 计算剩余秒数，减少定时器漂移。
- 使用 Canvas 绘制圆形进度环。
- 支持暂停、继续、重置当前泡、重新开始。
- 计时结束后调用 `wx.vibrateShort()` 震动提醒，并弹出“出汤”提示。

## 14. 品茶日记

涉及文件：

- 前端：`miniapp/pages/journal/journal.js`、`miniapp/pages/journal/edit.js`
- 后端：`backend/api/journal.py`
- 数据模型：`backend/models/journal.py`

实现方式：

1. 用户进入编辑页，填写茶名、茶类、产地、冲泡水温、冲泡时间、投茶量、香气评分、口感评分、综合评分、风味标签、笔记。
2. 风味标签在前端本地配置，最多选择 5 个。
3. 用户可选择一张图片。
4. 保存时，如果有图片，前端先调用 `/api/journal/upload` 上传图片。
5. 后端校验登录、图片类型和大小。
6. 后端复用识别模块的图片压缩函数保存日记图片，文件名前缀为 `journal_`。
7. 图片上传成功后返回 `/uploads/xxx`。
8. 前端再调用 `POST /api/journal` 保存文字内容和图片地址。
9. 后端对茶名、产地、标签、笔记等字段做长度限制和安全清理。
10. 日记写入 `tea_journal` 表。

列表与删除：

- `GET /api/journal` 按创建时间倒序返回当前用户的日记，支持分页。
- 后端将逗号分隔的 `flavor_notes` 转换为数组返回。
- 前端列表页拼接 `BASE_URL` 展示图片。
- `DELETE /api/journal/{jid}` 删除当前用户自己的日记。

## 15. 茶知识问答

涉及文件：

- 前端：`miniapp/pages/quiz/quiz.js`
- 后端：`backend/api/quiz.py`
- 数据模型：`backend/models/quiz.py`

实现方式：

- 题库在后端 `QUESTIONS` 常量中维护。
- 每道题包含题目、选项、正确答案索引和解析。
- `/api/quiz/questions` 使用 `random.sample()` 随机抽题。
- 返回题目时不返回正确答案，但返回解析用于前端判题展示。
- 默认抽取 10 题，接口限制 count 范围为 5 到 20。

判题流程：

- `/api/quiz/judge` 用于答题过程中的即时判分，不需要登录，不保存记录。
- `/api/quiz/submit` 用于最终提交，需要登录。
- 后端根据题目 ID 建立题目索引，逐题比较用户答案和正确答案。
- 返回每题是否正确、用户答案、正确答案、解析和选项。
- 提交后将总分和总题数写入 `quiz_record` 表。

评级规则：

- 正确率 >= 90%：茶圣
- 正确率 >= 70%：茶师
- 正确率 >= 50%：茶友
- 其他：茶小白

答题历史：

- `/api/quiz/history` 返回当前用户历史成绩。
- 按创建时间倒序排列，支持分页。

## 16. 茶叶估价

涉及文件：

- 前端：`miniapp/pages/valuation/valuation.js`
- 后端：`backend/api/valuation.py`
- LLM 客户端：`ai_models/llm/ollama_client.py`

实现方式：

1. 前端收集茶名、茶类、年份、外观描述、存储条件、产地。
2. 请求 `POST /api/valuation`。
3. 后端使用 Pydantic 限制字段长度和年份范围。
4. 后端构造“资深六堡茶鉴定专家”提示词。
5. 提示词要求 LLM 只返回 JSON。
6. 后端调用 `chat_completion()`。
7. 后端从 LLM 文本中截取首尾 `{}` 并尝试 `json.loads()`。
8. 解析成功则返回结构化估价结果。
9. 解析失败则把 LLM 文本作为 `analysis` 返回。
10. 调用异常时返回本地固定兜底估价。

返回字段包括：

- `quality_score`：品质评分
- `quality_level`：品质等级
- `price_min` / `price_max`：参考价格区间
- `analysis`：品质分析
- `storage_advice`：存储建议
- `brew_advice`：冲泡建议

## 17. 茶叶推荐

涉及文件：

- 前端：`miniapp/pages/recommend/recommend.js`
- 后端：`backend/api/recommend.py`
- LLM 客户端：`ai_models/llm/ollama_client.py`

实现方式：

1. 前端收集口味偏好、预算范围、饮用目的、健康需求、季节。
2. 请求 `POST /api/recommend`。
3. 后端通过映射表将选项值转换为中文描述。
4. 后端构造“六堡茶推荐专家”提示词。
5. 提示词要求推荐 3 款茶，并以 JSON 格式返回。
6. 后端调用 `chat_completion()`。
7. 后端尝试从 LLM 返回中解析 JSON。
8. 解析成功则返回推荐列表。
9. 解析失败则返回文本 summary。
10. 调用异常时返回本地兜底推荐。

推荐结果包括：

- 茶名
- 类型
- 参考价格区间
- 推荐理由
- 冲泡建议
- 匹配度
- 总体建议

## 19. 数据库初始化与种子数据

涉及文件：

- 数据库配置：`backend/database/mysql.py`
- 初始化脚本：`backend/database/init_db.py`
- 模型目录：`backend/models/`

实现方式：

- `USE_SQLITE=true` 时默认使用 `sqlite:///./backend/liubao_tea.db`。
- `USE_SQLITE=false` 时必须配置 MySQL `DATABASE_URL`。
- `Base.metadata.create_all(bind=engine)` 自动创建表。
- 知识库导入逻辑会先判断 `KnowledgeBase` 是否已有数据，避免重复导入。
- 产区导入逻辑会先判断 `Region` 是否已有数据，避免重复导入。
- 命令行执行 `python backend/database/init_db.py --force` 可强制清空知识库和产区后重新导入。

主要数据表：

- `user`：用户 openid、昵称、头像。
- `recognition_record`：图片识别记录。
- `qa_record`：智能问答记录。
- `favorite`：收藏记录。
- `knowledge_base`：知识库文章。
- `regions`：六堡茶产区。
- `tea_journal`：品茶日记。
- `quiz_record`：答题成绩。

## 21. 安全与降级设计

输入安全：

- openid、昵称、问题、收藏内容、日记内容等都会做清理。
- HTML 标签和危险字符会被移除。
- 图片接口限制 MIME 类型和大小。
- 删除历史、收藏、日记时会校验数据归属。

运行降级：

- 未配置微信密钥时，登录接口降级为开发模式 openid。
- Ollama 本地模型不可用时，问答、估价、推荐使用本地兜底内容。
- 未配置 embedding key 时，RAG 使用本地伪向量保证索引流程可运行。
- 未放置 YOLO 权重时，识别接口返回“模型未加载”提示。
- 向量检索失败时，知识库搜索回退到 SQL 模糊搜索。

需要注意：

- `.env.example` 应只保留占位符，不能提交真实 API Key。
- `miniapp/utils/config.js` 中的 `BASE_URL` 是环境相关配置，本地开发、真机调试和部署环境需要分别调整。
- `backend/uploads/`、SQLite 数据库、FAISS 索引属于运行时产物，不应提交到仓库。
